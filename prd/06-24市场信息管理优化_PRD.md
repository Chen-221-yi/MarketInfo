# 06-24 市场信息管理优化 PRD

生成日期：2026-06-25

资料依据：`docs/06-24 市场信息管理优化.txt`

文档定位：本文基于 2026-06-24 会议内容和已明确的 6 个优化点，整理市场信息管理系统下一轮优化需求。本文用于需求确认和后续宜搭实施，不包含具体 `formUuid`、`fieldId` 等技术 ID。

## 1. 背景与目标

当前市场信息管理系统已经覆盖联系人、单位、拜访记录、情报线索、项目等核心对象，但会议现场试用时暴露出几个问题：

| 问题 | 影响 |
| --- | --- |
| 单位所属系统选项不完整 | 省级、市县级单位分类不准，后续筛选和统计价值不足 |
| 拜访记录生成线索时字段重复 | 填报人不知道“交流内容、情报内容、下一步动作”分别写什么，容易重复录入 |
| 拜访主题默认示例不符合业务习惯 | 用户容易按时间或人员命名，列表中看不出拜访事项 |
| 线索提醒缺少明确接收人 | 线索记录完后无法指派谁必须看到、谁到期跟进 |
| 最近拜访记录中“上门”和“微信”颜色不易区分 | 上门拜访的重要性在列表中不够突出 |
| 拜访产生项目的闭环不足 | 线索能否转化为项目、一个线索产生多个项目无法清楚沉淀 |

本次优化目标：

1. 让单位、拜访、线索、项目之间的业务关系更清晰。
2. 降低一线人员填报成本，避免同一内容反复填写。
3. 支持“拜访 - 线索 - 提醒 - 跟进 - 项目转化”的闭环管理。
4. 为后续市场绩效、拜访排行、线索贡献统计提供数据基础。

## 3. 用户角色

| 角色 | 主要诉求 |
| --- | --- |
| 一线市场人员 | 快速记录拜访、提炼线索、指定跟进人，不重复填同一内容 |
| 部门经理 | 查看本部门拜访、线索、项目转化情况，点评记录，督促跟进 |

## 4. 业务对象与关系

### 4.1 核心对象

| 对象 | 业务含义 |
| --- | --- |
| 单位档案 | 联系人所在机构、项目相关单位、政府部门或合作单位 |
| 联系人 | 需要长期维护的关键人员 |
| 拜访记录 | 每一次上门、电话、微信、会议等接触事实 |
| 情报线索 | 从拜访或其他来源沉淀出的可跟进市场信息 |
| 项目明细 | 从线索转化出来的具体项目机会，不等同于完整项目管理流程 |
| 提醒任务 | 针对线索或拜访后续动作产生的到期提醒 |
| 评论/点评 | 管理者或协同人员对拜访、线索的补充意见和要求 |

### 4.2 数据关系

| 关系 | 说明 |
| --- | --- |
| 一个联系人可以有多条拜访记录 | 多人可围绕同一联系人分别记录拜访 |
| 一条拜访记录可以产生多条情报线索 | 例如一次拜访同时产生政策动向、项目线索、请款提醒 |
| 一个情报线索可以关联多条拜访记录 | 同一个线索可能由多个人、多次拜访共同推进 |
| 一个情报线索可以产生多个项目明细 | 会议明确提到“一个线索可以产生六个项目”也应支持 |
| 项目明细可以后续关联既有项目管理或招投标流程 | 本次先解决市场线索转项目的沉淀，不强行替代项目管理 |

## 5. 功能需求

### R1. 单位信息“所属系统”选项补全

#### 需求说明

单位档案中的“所属系统”需要覆盖常见政府和业务系统，会议中明确提到至少要补充发改、应急等系统，并希望整体选项达到约二三十个，便于省级、市级、区县级单位归类。

#### 建议选项

| 字段 | 类型 | 建议选项 |
| --- | --- | --- |
| 所属系统 | 单选 | 发改、财政、应急、公安、住建、自然资源、规划、城管、水利、农业农村、交通、生态环境、文旅、体育、教育、卫健、民政、人社、经信/工信、数据/政务服务、公共资源交易、国资、司法/政法、林业、园林、招商、综合、其他 |

#### 规则

1. 保留“其他”，并提供备注字段承接未覆盖系统。
2. “单位级别”继续支持省级、市级、区县级、乡镇级、其他。
3. 地址字段非核心场景下不强制必填，避免新增单位时卡住录入。
4. 后续单位列表、筛选、统计应使用补全后的系统选项。

#### 验收标准

1. 新增/编辑单位时能选择发改、应急等新增系统。
2. 单位列表筛选项同步显示新增系统。
3. 旧数据不丢失，原所属系统值仍能正常展示和筛选。

### R2. 拜访主题默认提示改为以拜访内容/事由为主

#### 需求说明

会议现场认为原拜访主题默认示例偏“时间 + 人员”，不利于列表快速判断拜访目的。拜访主题应以拜访内容、业务事项、项目事由为主。

#### 字段调整

| 字段 | 当前问题 | 调整后要求 |
| --- | --- | --- |
| 拜访主题 | 默认示例类似“某时间后拜访某人”，不能体现事项 | 默认提示改为“例如：关于全省文体专项规划项目交流”“关于某项目请款/签合同/资料准备沟通” |

#### 填写规则

1. 拜访主题优先表达“为什么拜访”，而不是只写“拜访了谁”。
2. 推荐格式：`关于 + 事项/项目/工作 + 的沟通`。
3. 联系人、单位、拜访时间仍通过关联字段和时间字段表达，不要求写进主题。
4. 若系统自动生成主题，应优先使用“事项/项目名称 + 拜访方式”，不要只拼接联系人姓名。

#### 验收标准

1. 新增拜访记录时，默认提示文本已替换为内容型示例。
2. 最近拜访列表中，用户仅看主题即可大致判断业务事项。

### R3. 拜访记录生成情报线索时去除字段重复

#### 需求说明

会议现场发现，拜访记录中的交流内容、情报线索明细中的情报内容、下一步动作容易重复。需要明确字段边界，减少重复录入。

#### 字段边界

| 字段 | 所属对象 | 应填写内容 | 不应填写内容 |
| --- | --- | --- | --- |
| 交流内容 | 拜访记录 | 本次实际聊了什么、获得了什么事实信息 | 下一步谁去做什么的任务安排 |
| 线索标题 | 情报线索明细 | 对线索的一句话概括 | 大段拜访原文 |
| 线索分类 | 情报线索明细 | 市场信息、项目线索、政策动向、招采节点、请款/合同、其他 | 具体执行动作 |
| 下一步动作 | 情报线索明细 | 后续谁、在什么时间前、要推进什么 | 与交流内容重复的事实描述 |
| 线索说明 | 情报线索明细 | 仅当线索与拜访交流内容不能对应时补充说明 | 与交流内容完全相同的内容 |

#### 调整方案

1. 拜访记录内的情报线索明细不再要求必填“情报内容”。
2. 将“情报内容”调整为非必填的“线索说明”，或在拜访表单内隐藏，只在独立线索详情中展示。
3. 生成独立情报线索时：
   - 线索标题来自明细中的“线索标题”。
   - 线索说明优先使用明细中的“线索说明”。
   - 若线索说明为空，则线索详情展示来源拜访记录中的交流内容摘要。
   - 下一步动作单独映射到线索跟进字段。
4. 拜访详情页展示线索时，应同时显示“来源拜访”和“下一步动作”，但避免两个区域出现完全相同的正文。

#### 验收标准

1. 新增拜访并选择“是否产生线索 = 是”时，用户不需要重复填写同一段内容。
2. 独立情报线索详情仍能看清来源事实和后续动作。
3. 历史数据中的情报内容不丢失，可兼容展示。

### R4. 情报线索明细增加提醒人，到期自动提醒

#### 需求说明

线索不是只记录完就结束，需要指定哪些人必须看到、哪些人到期跟进。会议中多次提到要能“艾特”指定人员，例如指定李阳、孙总、财务、行政等，并在提醒日期前后通过系统提醒。

#### 字段设计

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 提醒人/跟进人 | 成员，多选 | 否 | 需要看到或跟进此线索的人 |
| 下一步动作 | 多行文本 | 否 | 后续计划、跟进要求 |
| 提醒日期 | 日期 | 否 | 需要系统提醒的日期 |
| 提前提醒天数 | 数值/单选 | 否 | 默认 2 天，可配置 |
| 跟进状态 | 单选 | 是 | 待跟进、跟进中、已转项目、已关闭 |
| 已提醒时间 | 日期时间 | 否 | 系统自动记录 |
| 最近查看时间 | 日期时间 | 否 | 用于判断提醒人是否已看到，若宜搭能力支持 |

#### 提醒规则

1. 当提醒人和提醒日期均有值时，系统按提醒日期自动发送工作通知或待办。
2. 默认提前 2 天提醒。例如提醒日期为 15 日，则可在 13 日生成提醒。
3. 提醒对象为“提醒人/跟进人”中选择的人员。
4. 线索状态为已转项目、已关闭时，不再继续发送到期提醒。
5. 未产生线索但仍有后续动作的拜访记录，是否也支持提醒需要确认。建议第一阶段先在线索明细中实现，第二阶段再扩展到普通拜访后续动作。

#### 通知内容

通知至少包含：

| 内容 | 说明 |
| --- | --- |
| 线索标题 | 让接收人知道是哪条线索 |
| 下一步动作 | 告诉接收人要做什么 |
| 来源拜访 | 可跳转到来源拜访记录 |
| 提醒日期 | 说明当前提醒原因 |
| 记录人 | 知道是谁发起的线索 |

#### 验收标准

1. 用户在拜访记录的线索明细中可以选择一个或多个提醒人。
2. 到达提醒时间后，提醒人能收到系统通知或待办。
3. 提醒人打开通知后能进入对应线索或来源拜访。
4. 线索关闭或转项目后不再重复提醒。

### R5. 最近拜访记录中上门、微信背景色区分

#### 需求说明

最近拜访记录列表中，拜访方式需要更直观地区分。会议中明确指出“上门”和“微信”不能使用相同或过于接近的背景色，因为上门拜访更重要。

#### 展示规则

| 拜访方式 | 展示要求 |
| --- | --- |
| 上门 | 使用更高强调度的颜色，突出显示 |
| 微信 | 使用与上门明显不同的轻量颜色 |
| 电话 | 使用中性颜色 |
| 会议/饭局/培训会/活动 | 保持现有风格或按类别区分 |

#### 验收标准

1. 最近拜访记录中，“上门”和“微信”标签颜色肉眼可明显区分。
2. 上门拜访的视觉优先级高于微信、电话。
3. 调整不影响拜访方式筛选和历史数据展示。

### R6. 拜访记录增加“是否产生项目”和项目明细表

#### 需求说明

会议明确提出，拜访记录除了“是否产生线索”，还要增加“是否产生项目”。一个线索后续可能产生多个项目，项目明细应能沉淀在系统内，形成市场信息闭环。

#### 字段设计

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 是否产生项目 | 单选 | 是 | 是、否 |
| 项目明细 | 子表单 | 条件必填 | 当是否产生项目为“是”时展示 |

#### 项目明细子表字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 项目名称 | 单行文本 | 是 | 从拜访或线索产生的具体项目机会名称 |
| 关联线索 | 关联表单 | 否 | 关联已存在的情报线索 |
| 项目类型 | 单选 | 否 | 规划、测绘、数据、平台、服务、招采、其他 |
| 牵头单位 | 关联表单/单行文本 | 否 | 相关单位 |
| 关联联系人 | 关联表单 | 否 | 相关联系人 |
| 项目阶段 | 单选 | 否 | 待判断、可跟进、推进中、已立项、已放弃、已转投标/项目管理 |
| 预计发生时间 | 日期 | 否 | 预计启动或发生时间 |
| 有效截止日期 | 日期 | 否 | 线索/机会有效截止 |
| 项目负责人 | 成员 | 否 | 我方后续负责人 |
| 预计金额/规模 | 数值/单行文本 | 否 | 无法明确时可暂空 |
| 下一步动作 | 多行文本 | 否 | 项目机会下一步推进要求 |
| 备注 | 多行文本 | 否 | 其他说明 |

#### 业务规则

1. “是否产生项目”表达的是是否产生我方需要跟进的项目机会，不是外部世界是否客观存在项目。
2. 如果外部已有项目，但我方无机会、无跟进价值，可以选择“否”，并在交流内容或备注中说明原因。
3. 一条拜访记录可以产生多个项目明细。
4. 一个情报线索可以产生多个项目明细。
5. 当线索产生项目后，线索状态可更新为已转项目或部分转项目。
6. 项目明细后续可关联既有项目管理或招投标流程，但本次不强制打通完整招投标流程。

#### 验收标准

1. 新增拜访记录时可以选择“是否产生项目”。
2. 选择“是”后可以填写一条或多条项目明细。
3. 线索详情中能看到该线索已产生的项目明细数量和列表。
4. 项目明细能反查来源拜访和来源线索。

### R7. 增加线索管理视角

#### 需求说明

会议中多次讨论“以人为线”和“以线索为头”的关系。联系人管理仍保留，但市场推进应能以线索为主线查看：一个线索下有多少人拜访、拜访了几次、目前到什么阶段、有没有转项目。

#### 功能设计

| 功能 | 说明 |
| --- | --- |
| 线索管理入口 | 在首页/侧边导航/联系人详情中提供入口 |
| 线索列表 | 展示所有线索，支持搜索、筛选、排序 |
| 线索详情 | 展示线索基础信息、来源拜访、关联联系人、跟进记录、提醒、项目明细 |
| 关联拜访记录 | 一个线索下可看到多次拜访记录 |
| 跟进阶段 | 用简单状态表达线索进度 |
| 拜访次数统计 | 统计该线索关联的拜访次数，辅助判断成熟度 |

#### 线索列表建议字段

| 字段 | 说明 |
| --- | --- |
| 线索标题 | 核心事项 |
| 线索分类 | 市场信息、项目线索、政策动向、招采节点等 |
| 重要程度 | 高、中、低 |
| 跟进状态 | 待跟进、跟进中、已转项目、已关闭 |
| 关联单位 | 相关单位 |
| 关联联系人 | 相关联系人 |
| 跟进人/提醒人 | 当前需要跟进的人 |
| 提醒日期 | 下一次提醒时间 |
| 拜访次数 | 该线索关联拜访记录数量 |
| 项目数量 | 已产生项目明细数量 |
| 最近更新时间 | 最近拜访或线索更新时间 |

#### 成熟度建议

第一阶段不做复杂算法，仅做简单展示：

| 口径 | 展示 |
| --- | --- |
| 1 到 2 次拜访 | 初步接触 |
| 3 到 5 次拜访 | 持续跟进 |
| 6 次及以上拜访 | 重点推进 |
| 已产生项目 | 已转项目或部分转项目 |

#### 验收标准

1. 管理者可以从线索视角查看所有市场线索。
2. 打开一条线索后能看到它关联的拜访记录和项目明细。
3. 线索列表能筛选待跟进、即将提醒、已转项目等状态。

### R8. 评论、权限、必看人和榜单统计配套优化

#### 需求说明

会议中提到，拜访记录和线索不仅要填报，还需要被点评、被指定查看，并且不能让无关人员误改敏感信息。后续市场绩效也希望和上门拜访、线索贡献、项目转化形成正相关。

#### 评论/点评

| 需求 | 说明 |
| --- | --- |
| 每条拜访记录可评论 | 管理者可指出信息不完整、要求补充资金来源、投资主体等 |
| 每条线索可评论 | 对线索真实性、推进方向、下一步动作进行补充 |
| 支持 @ 人 | 评论时可提醒相关人员查看 |
| 不直接改原记录 | 普通评论不应覆盖填报人的原始内容 |
| 保留变更记录 | 若确需编辑原记录，应可追溯修改人和修改时间 |

#### 权限

| 场景 | 要求 |
| --- | --- |
| 普通员工 | 可查看自己相关、被授权、被提醒的记录；不能随意修改他人记录 |
| 部门经理 | 可查看本部门拜访、线索、项目明细，并可点评 |
| 管理层 | 可查看全局数据，但敏感字段仍按授权控制 |
| 敏感信息 | 高星级联系人、重要职务联系人、手机号、私密画像等需要控制展示 |
| 授权查看人 | 对高敏线索、联系人、项目明细应继续生效 |

#### 榜单/绩效统计

| 指标 | 说明 |
| --- | --- |
| 上门拜访数 | 用于体现真实市场动作 |
| 线索数 | 统计个人或部门贡献的有效线索 |
| 转项目数 | 统计线索产生项目明细数量 |
| 跟进完成率 | 统计提醒任务是否按时处理 |
| 记录质量 | 可结合经理点评，暂不做复杂自动评分 |

第一阶段仅提供数据展示和统计，不直接调整绩效发放公式。会议中提到“暂时不要强相关，但以后肯定有相关”，因此建议先打通数据口径。

## 7. 流程设计

### 7.1 拜访记录到线索

1. 用户进入联系人详情或拜访记录页，点击“记录拜访”。
2. 填写拜访主题、联系人、单位、方式、时间、地点、交流内容。
3. 选择“是否产生线索”。
4. 如果选择“是”，填写一条或多条线索明细：
   - 线索标题
   - 线索分类
   - 重要程度
   - 下一步动作
   - 提醒人/跟进人
   - 提醒日期
5. 保存拜访记录。
6. 系统生成或同步独立情报线索。
7. 后续从线索详情继续跟进。

### 7.2 线索提醒

1. 用户在线索明细中选择提醒人和提醒日期。
2. 系统按默认提前天数检查即将到期线索。
3. 到期前向提醒人发送工作通知或待办。
4. 提醒人打开通知，进入线索或来源拜访。
5. 跟进后更新下一步动作、状态或新增拜访记录。
6. 线索已关闭或已转项目后，停止继续提醒。

### 7.3 线索转项目

1. 用户在拜访记录或线索详情中选择“是否产生项目 = 是”。
2. 填写一条或多条项目明细。
3. 项目明细关联来源线索和来源拜访。
4. 线索详情展示项目明细列表。
5. 若项目进入正式推进，可后续关联项目管理或招投标流程。

### 7.4 评论和点评

1. 管理者打开拜访记录或线索详情。
2. 在评论区补充问题、判断或要求。
3. 可 @ 指定人员查看。
4. 被 @ 人收到通知后补充记录或更新跟进。
5. 原始拜访记录不因评论被覆盖。
